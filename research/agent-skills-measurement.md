# Measuring Agent Skills compliance and quality

**Scope.** This note separates (1) conformance to the cross-client Agent Skills format from (2) whether a skill improves an agent on its intended tasks. The first is mostly deterministic; the second is empirical and client/model-dependent. All source links below were accessed **2026-09-16**.

## Executive answer

Use a **gated, two-layer evaluation**:

1. **Conformance gate (must pass):** parse the package and check the current Agent Skills specification mechanically: a skill directory has an exact `SKILL.md`; its YAML frontmatter has valid required metadata; the name matches the directory and all limits/character rules; and optional metadata has the specified types. **Recommendation:** also require every referenced resource to resolve. Run the official `skills-ref validate` command, but supplement it because the reference library is a demonstration implementation, not a complete quality or security audit. [SPEC](https://agentskills.io/specification.md) · [REF](https://github.com/agentskills/agentskills/blob/547831f3a23724ba64a9b79bbf59c5e0bc8f2d1a/skills-ref/README.md) · [VALIDATOR](https://github.com/agentskills/agentskills/blob/547831f3a23724ba64a9b79bbf59c5e0bc8f2d1a/skills-ref/src/skills_ref/validator.py)
2. **Effectiveness evaluation (must be evidenced):** run realistic tasks in clean, isolated contexts both with and without the skill (or against a frozen previous version); grade observable assertions with concrete evidence; measure activation, output quality, reliability, cost, and side effects; inspect traces and have a human review outputs. This is the official eval-driven workflow. [EVAL](https://agentskills.io/skill-creation/evaluating-skills.md) · [TRIGGER](https://agentskills.io/skill-creation/optimizing-descriptions.md)

As of the access date, the official specification and documentation provide a **per-skill eval procedure**, not a required cross-skill benchmark, universal score, or leaderboard. The weighted score and release thresholds proposed below are therefore recommendations, not Agent Skills requirements. [SPEC](https://agentskills.io/specification.md) · [EVAL](https://agentskills.io/skill-creation/evaluating-skills.md) · [REF](https://github.com/agentskills/agentskills/blob/547831f3a23724ba64a9b79bbf59c5e0bc8f2d1a/skills-ref/README.md)

## Keep standard conformance separate from client behavior

The **generic standard** defines the skill package and `SKILL.md` format. It does not mandate where a client installs skills or how it activates them. Client integration guidance says discovery locations, activation mechanisms, collision policy, permissions, and loading details vary by implementation. `allowed-tools` is explicitly experimental and support may vary. [SPEC](https://agentskills.io/specification.md) · [CLIENT](https://agentskills.io/client-implementation/adding-skills-support.md)

A Claude, IDE, or other client may add product-specific limits, supported tools, permissions, or packaging rules. Test those separately and record the client/version; do not report a client-specific rule as cross-client conformance. For example, the standard's `description` limit is 1–1024 characters, while product documentation may impose a different operational limit. [SPEC](https://agentskills.io/specification.md) · [CLAUDE](https://support.claude.com/en/articles/12512198-creating-custom-skills)

## Layer 1: conformance gates and recommended safety gates

A conformance failure is a standard failure. The resource-integrity and safety checks below are release-policy recommendations unless explicitly identified as specification rules.

| Gate | Mechanical or review check | Evidence to retain |
|---|---|---|
| Package shape | The skill is a directory containing an exact `SKILL.md` at minimum. The standard allows additional files/directories; `scripts/`, `references/`, and `assets/` are conventions, not required structure. [SPEC](https://agentskills.io/specification.md) | Directory listing and a hash of every shipped file. |
| Frontmatter parse | `SKILL.md` starts with YAML frontmatter and is followed by Markdown. Frontmatter is a mapping, not malformed YAML or another document type. [SPEC](https://agentskills.io/specification.md) | Parser/validator version, command output, and parsed metadata (redacted if necessary). |
| Required metadata | `name` and `description` exist, are non-empty strings, and are within the specification's limits. [SPEC](https://agentskills.io/specification.md) | Parsed values, character counts, and validator output. |
| Name rules | `name` is 1–64 characters, lowercase Unicode alphanumeric plus hyphens, has no leading/trailing or consecutive hyphens, and equals the parent directory name. [SPEC](https://agentskills.io/specification.md) | Exact name, directory name, normalization policy, and a pass/fail result. |
| Optional metadata | If present, `license` is a license name/reference; `compatibility` is 1–500 characters and states environment requirements; `metadata` is a string-to-string map; `allowed-tools` is treated as experimental and tested only where the target client supports it. [SPEC](https://agentskills.io/specification.md) | Parsed field types/lengths and target-client support declaration. |
| Resource integrity | **Proposed release gate:** every path named by the body exists, is relative to the skill root, and is readable under the target client. Relative root paths and shallow reference chains are the portable pattern recommended by the specification. [SPEC](https://agentskills.io/specification.md) | A resolved-reference manifest and failed-path report. |
| Official validator | Run `skills-ref validate ./my-skill` and retain the result. The reference implementation checks frontmatter and naming conventions. Its parser accepts lowercase `skill.md`, whereas the specification names `SKILL.md`; therefore a lowercase file should fail a strict standard gate even if this implementation accepts it. The validator also does not substitute for checking every optional-field type, resource reference, behavior, or security property. [SPEC](https://agentskills.io/specification.md) · [VALIDATOR](https://github.com/agentskills/agentskills/blob/547831f3a23724ba64a9b79bbf59c5e0bc8f2d1a/skills-ref/src/skills_ref/validator.py) · [PARSER](https://github.com/agentskills/agentskills/blob/547831f3a23724ba64a9b79bbf59c5e0bc8f2d1a/skills-ref/src/skills_ref/parser.py) · [REF](https://github.com/agentskills/agentskills/blob/547831f3a23724ba64a9b79bbf59c5e0bc8f2d1a/skills-ref/README.md) | Exact command, package/version or commit, stdout/stderr, and supplemental-check results. |
| Trust and safety review | **Official security guidance + proposed release gate:** malicious skills can exfiltrate data or cause unintended actions, so audit bundled files, dependencies, resources, scripts, and network instructions; project-level skills may also come from untrusted repositories. [SECURITY](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills) · [CLIENT](https://agentskills.io/client-implementation/adding-skills-support.md) | Reviewer checklist, dependency/network inventory, sandbox permissions, and any rejected operation. |

**Strict-gate recommendation.** Treat missing/invalid format, unresolved required resources, or any unauthorized secret access, network access, file mutation, or destructive action as a release failure. This zero-tolerance policy is a proposed safety policy derived from the official security warnings, not a normative field in the format. [SECURITY](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)

## Layer 2: quality and effectiveness dimensions

The official guidance emphasizes real tasks, execution traces, trigger behavior, assertions, timing/tokens, comparison with a baseline, iteration, and human review. It does not prescribe weights or thresholds. [BEST](https://agentskills.io/skill-creation/best-practices.md) · [EVAL](https://agentskills.io/skill-creation/evaluating-skills.md) · [TRIGGER](https://agentskills.io/skill-creation/optimizing-descriptions.md)

The following is a **proposed 100-point rubric**, applied only after all hard gates pass. Score each dimension from 0 (absent/failing) to 4 (strong), then calculate `weight × score / 4`.

| Dimension | Weight | Evidence and proposed 0–4 anchors |
|---|---:|---|
| Task success and completeness | 35 | Assertion pass rate and human judgment on the intended outcome. **4:** all critical assertions pass in at least 90% of repeated runs and no material defect; **3:** at least 80%, with only minor defects; **2:** 60–79% or a significant omission; **1:** 1–59%; **0:** no useful result or critical failure. Use domain-specific assertions rather than generic “good output.” [EVAL](https://agentskills.io/skill-creation/evaluating-skills.md) |
| Activation precision and recall | 20 | For labeled should-trigger and should-not-trigger prompts, record whether `SKILL.md` was loaded. **4:** both positive recall and negative abstention at least 90%; **3:** both at least 80%; **2:** both at least 65%; **1:** one is below 65%; **0:** activation is unobserved or systematically wrong. These thresholds are recommendations; the official guidance recommends about 20 varied queries and three runs per query. [TRIGGER](https://agentskills.io/skill-creation/optimizing-descriptions.md) |
| Reliability and repeatability | 15 | Re-run the same case in clean contexts and report mean pass rate and standard deviation. **4:** no critical flake and standard deviation ≤0.10; **3:** ≤0.20; **2:** ≤0.30; **1:** higher variance or intermittent critical defects; **0:** cannot reproduce or observe runs. Standard deviation is meaningful only with multiple runs. [EVAL](https://agentskills.io/skill-creation/evaluating-skills.md) |
| Safety and instruction boundaries | 15 | Trace/tool audit and adversarial cases. **4:** no unauthorized access, secret handling, destructive action, or boundary violation; **3:** only harmless, clearly surfaced warnings; **2:** recoverable unsafe attempt; **1:** serious near miss; **0:** any critical safety violation (also a hard-gate failure). This weighting and the test set are recommendations based on official security guidance. [SECURITY](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills) · [CLIENT](https://agentskills.io/client-implementation/adding-skills-support.md) |
| Efficiency and progressive disclosure | 10 | Compare tokens, duration, and resource loads with the same baseline. **4:** materially better success without disproportionate cost; **3:** useful gain with ≤50% proposed overhead; **2:** gain but >50% overhead or unclear resource loading; **1:** cost rises without a clear gain; **0:** no measurements. The specification recommends keeping the main `SKILL.md` under 500 lines and under 5,000 tokens, but these are recommendations, not pass/fail format rules. [SPEC](https://agentskills.io/specification.md) · [EVAL](https://agentskills.io/skill-creation/evaluating-skills.md) |
| Portability and operability | 5 | Test relative references, declared dependencies, scripts, and each target client. **4:** works across all declared targets with no undocumented prerequisite; **3:** one documented minor adaptation; **2:** manual repair required; **1:** works only in one unqualified environment; **0:** cannot run. Script guidance recommends pinned versions, non-interactive interfaces, helpful errors, structured output, and documented prerequisites. [SCRIPTS](https://agentskills.io/skill-creation/using-scripts.md) |

**Proposed decision rule:** release only when all hard gates pass, the total is at least 80/100, task success is at least 3/4, and safety has no critical violation. Mark 65–79 as conditional and iterate; below 65 is not ready. Report the component scores and raw counts, not just the total. These numerical cutoffs are policy recommendations, not official standard requirements.

## Repeatable evaluation protocol

1. **Freeze the artifact and environment.** Record the skill commit/hash, every bundled-file hash, target client and version, model/version/settings, tool permissions, dependency lock, OS/runtime, test-fixture hashes, and evaluator version. Do not change the skill or harness during a comparison.
2. **Run static gates first.** Execute `skills-ref validate ./skill`; a conforming package should exit 0 and print `Valid skill: ...`, while validation errors exit 1. Add checks for exact uppercase `SKILL.md`, metadata types, non-empty compatibility when supplied, reference resolution, dependency declarations, and dangerous capabilities. Store machine-readable results and a human audit. [CLI](https://github.com/agentskills/agentskills/blob/547831f3a23724ba64a9b79bbf59c5e0bc8f2d1a/skills-ref/src/skills_ref/cli.py)
3. **Build two linked test sets.** Create (a) activation queries labeled should-trigger/should-not-trigger and (b) task cases with prompt, expected outcome, optional input files, and assertions. Start with 2–3 task cases as the official guidance suggests, then expand after the first run. Keep a fixed validation/holdout split; the trigger guidance recommends roughly 60% train and 40% validation to avoid description overfitting. [EVAL](https://agentskills.io/skill-creation/evaluating-skills.md) · [TRIGGER](https://agentskills.io/skill-creation/optimizing-descriptions.md)
4. **Run matched controls in clean contexts.** For every case, run the same prompt and files with the candidate skill and without it (or with a snapshot of the prior skill). Use fresh sessions/subagents so prior work cannot leak into the result. Preserve `with_skill/`, `without_skill/` or `old_skill/` outputs, transcripts, tool calls, and activation events. [EVAL](https://agentskills.io/skill-creation/evaluating-skills.md)
5. **Repeat enough to expose variance.** Run each activation query three times initially, as the official trigger guidance recommends. **Recommendation:** run each important task case at least three times and five or more times for high-risk decisions; report the raw count, mean, and standard deviation rather than hiding instability in an average. [TRIGGER](https://agentskills.io/skill-creation/optimizing-descriptions.md) · [EVAL](https://agentskills.io/skill-creation/evaluating-skills.md)
6. **Grade observable assertions.** Use code for checks such as valid JSON, file existence, schema, row counts, dimensions, or invariants. Use a rubric and human review for quality that cannot be reduced safely to a boolean. Every PASS must cite concrete output evidence; review the assertions themselves for being too easy, impossible, or unverifiable. [EVAL](https://agentskills.io/skill-creation/evaluating-skills.md)
7. **Aggregate both value and cost.** Report per-case pass rates, trigger recall/abstention, mean/stddev, token and duration deltas, resource-load counts, safety incidents, and with-skill minus baseline differences. Keep a case-level table: aggregate means can hide a catastrophic edge case. The official example records `timing.json`, assertion `grading.json`, and an iteration-level `benchmark.json`. [EVAL](https://agentskills.io/skill-creation/evaluating-skills.md)
8. **Review traces and outputs blind where possible.** Inspect the full execution trace for wasted steps, ignored instructions, unnecessary context loads, and unsafe tool calls. For candidate-version comparisons, show outputs without revealing which version produced which result. Have a domain reviewer record specific, actionable feedback for every case; human review catches failures not anticipated by assertions. [BEST](https://agentskills.io/skill-creation/best-practices.md) · [EVAL](https://agentskills.io/skill-creation/evaluating-skills.md)
9. **Iterate without contaminating the holdout.** Use failed assertions, human feedback, and traces to revise the skill; rerun the full fixed set in a new iteration directory, then select based on validation performance. Keep holdout prompts and expected outcomes hidden from the authoring loop. [EVAL](https://agentskills.io/skill-creation/evaluating-skills.md) · [TRIGGER](https://agentskills.io/skill-creation/optimizing-descriptions.md)

## Constructing good cases

### Activation matrix

The official trigger guidance recommends about 20 realistic queries, roughly balanced between positive and negative labels, run multiple times. [TRIGGER](https://agentskills.io/skill-creation/optimizing-descriptions.md)

- **Should trigger:** vary formal/casual wording, typos/abbreviations, explicit and implicit domain references, short and context-heavy prompts, and simple versus multi-step tasks. [TRIGGER](https://agentskills.io/skill-creation/optimizing-descriptions.md)
- **Should not trigger:** use near misses that share vocabulary but require a neighboring capability; unrelated prompts are too easy to reveal precision problems. [TRIGGER](https://agentskills.io/skill-creation/optimizing-descriptions.md)
- **Labels:** define “triggered” as an observed load of the candidate `SKILL.md`, not the model merely mentioning the skill. [TRIGGER](https://agentskills.io/skill-creation/optimizing-descriptions.md)

Report positive recall and negative abstention separately; a broad description can improve recall while silently degrading precision. **Recommendation:** use their harmonic mean as a single activation summary only in addition to the two component rates.

### Task matrix

- Use prompts a real user would type, with realistic file paths, domain context, and complete inputs where needed; vague prompts such as “process this data” do not test useful behavior. [EVAL](https://agentskills.io/skill-creation/evaluating-skills.md)
- Include at least one boundary case per major workflow: malformed input, missing field, unusual request, ambiguous instruction, or a case where the skill should decline or ask for clarification. [EVAL](https://agentskills.io/skill-creation/evaluating-skills.md)
- Define expected outcomes in human-readable terms before grading. Add assertions after an exploratory first round if necessary, then freeze them for comparisons. Prefer observable invariants over exact wording; the official guidance calls “good output” too vague and exact phrases too brittle. [EVAL](https://agentskills.io/skill-creation/evaluating-skills.md)
- Test bundled scripts as agent-facing interfaces: `--help`, required-argument errors, non-interactive execution, dependency availability, and structured output. These checks follow the official script guidance; they are not extra format fields. [SCRIPTS](https://agentskills.io/skill-creation/using-scripts.md)
- **Recommendation:** add untrusted-input and prompt-injection cases, permission-denied cases, secret-shaped fixtures, and network/destructive-operation attempts. The expected result should be safe refusal or explicit confirmation, as appropriate to the target client and task; the standard itself does not define a universal refusal policy. [SECURITY](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills) · [CLIENT](https://agentskills.io/client-implementation/adding-skills-support.md)

## Evidence and reproducibility checklist

A result is reproducible only if another evaluator can reconstruct the same input, context, and grading decision. Retain:

- candidate and baseline/previous-skill commits, complete package manifests, file hashes, and resolved relative-reference manifest;
- `skills-ref` version/commit and raw validator output, plus supplemental conformance output;
- client, model, system/tool configuration, dependency/runtime versions, OS/container image, randomness settings, and permissions;
- immutable prompt/input fixtures and their hashes, case labels, expected outcomes, assertion definitions, and train/validation/holdout membership;
- each run's transcript/tool calls/activation event, output files, `timing.json` token and duration data, and `grading.json` assertion results with evidence;
- reviewer identity/role, rubric version, blind-comparison mapping, concrete comments, and any redacted fields; and
- aggregate raw counts, means, standard deviations, deltas versus baseline, and safety incidents.

The directory layout and timing/grading artifacts above follow the official evaluation guide; recording the remaining provenance is a reproducibility recommendation. [EVAL](https://agentskills.io/skill-creation/evaluating-skills.md)

## Limitations and anti-gaming checks

- **Format is not capability.** A clean validator result proves metadata/package conformance, not that the agent activates the skill, follows it, or produces correct work. The official reference library itself is marked demonstration-only. [REF](https://github.com/agentskills/agentskills/blob/547831f3a23724ba64a9b79bbf59c5e0bc8f2d1a/skills-ref/README.md)
- **No universal official benchmark.** Per-skill evals make local progress measurable, but scores from unrelated skills are not automatically comparable because tasks, clients, models, and assertion sets differ. **Recommendation:** publish the case set, baseline, raw counts, and rubric with every score. [EVAL](https://agentskills.io/skill-creation/evaluating-skills.md)
- **Nondeterminism and small samples.** A single successful run is weak evidence. Repeat runs, report variance, and avoid presenting standard deviation as meaningful for a tiny one-run sample; the official guide makes the same statistical caution. [EVAL](https://agentskills.io/skill-creation/evaluating-skills.md)
- **Baseline confounding.** A skill may appear helpful because the baseline lacked a tool, file, or permission. Keep everything except skill loading matched, and test both a no-skill baseline and a previous-version baseline when improving an existing skill. [EVAL](https://agentskills.io/skill-creation/evaluating-skills.md)
- **Assertion gaming.** Assertions that always pass inflate scores; assertions that always fail may be broken or too hard. Remove or repair both, use objective invariants rather than brittle phrases, and retain human review. [EVAL](https://agentskills.io/skill-creation/evaluating-skills.md)
- **Prompt overfitting.** A description can memorize trigger queries. Keep a fixed validation split and add fresh, unseen queries after selecting an iteration. [TRIGGER](https://agentskills.io/skill-creation/optimizing-descriptions.md)
- **Judge and reviewer bias.** A model judge can favor a known version or style. Blind candidate comparisons, concrete evidence, calibrated human sampling, and executable checks reduce (but do not eliminate) this risk. [EVAL](https://agentskills.io/skill-creation/evaluating-skills.md)
- **Averages hide harm.** Report per-case results and make critical safety violations a hard failure; do not let a high mean compensate for an unsafe edge case. The hard-failure rule is a proposed policy grounded in the official security guidance. [SECURITY](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)
- **Cost-quality tradeoffs.** Tokens and duration are useful evidence, not a universal objective. A slower skill may be justified for a high-value task; compare success and cost together and state the operational tradeoff. [EVAL](https://agentskills.io/skill-creation/evaluating-skills.md)
